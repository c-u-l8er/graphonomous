# R2 — Evidence record formats, canonicalization, receipts, and projection digests for Graphonomous G0

Research report, 2026-09-02. Every URL below was accessed on 2026-09-02. "Measured" means run on this machine today (Python 3.13.14, Node v25.2.1, Elixir 1.19.4 / OTP 28, git 2.55.0).

## Executive summary

- **Adopt RFC 8785 (JCS) as the canonical form, shipped at G0 as a *restricted profile*.** Under the profile (integers only, within ±(2^53−1); ASCII keys; well-formed UTF-8 strings with no C0 controls except `\t` `\n` `\r`) the existing "sorted keys + compact + sha256" discipline is byte-identical to JCS in Python, Node and Elixir — measured, not assumed.
- **The `1.0` vs `1` defect is structural.** Python `json.dumps`, OTP `:json` and Jason all format floats unlike ECMAScript (`1e+20`/`1.0e20` vs `100000000000000000000`, `-0.0` vs `0`). Ban non-integer numbers from identity-bearing fields; carry them as decimal strings.
- **Normalized record** = one canonical JSON object with a stable logical id and a separate content hash, written `sha256:<64 lowercase hex>` (OCI digest grammar).
- **Receipt** = an in-toto Statement isomorph (`subject[]` of ResourceDescriptors, versioned `predicateType`, `predicate`) stored as a native record; DSSE, Sigstore and SLSA trust semantics are export adapters.
- **External artifacts are pointers, never bytes**: ResourceDescriptor + DigestSet (`sha256`, `gitCommit`, `gitTree`, `gitBlob`, `dirHash1`) + `uri`. Hash the tree, not the tarball, unless the tarball is built reproducibly.
- **Projection digest** = sha256 of a canonical manifest record of `(id, hash)` pairs sorted by id — order-independent by construction; leaves use RFC 9162 domain separation so a Merkle tree or transparency log can be layered later without re-hashing.
- **A git tree of canonical files is a witness, not the definition**: mode bits, the directory-as-`/` sort rule, the raw `40000` mode and the SHA-1 default all leak in.
- **Transparency logs wait, explicitly.** SCITT (RFC 9943, June 2026), COSE Receipts (RFC 9942) and Rekor v2 (GA 2025-10-10) all presume many issuers and external relying parties; G0 has one writer and a git history.
- **Lineage**: an adapter run record puts inputs, adapter and outputs by digest plus deterministic params in an identity part and times/host in a witness part; OpenLineage and PROV-JSON are exports.
- **Validation**: JSON Schema 2020-12 for shape, a custom validator for ledger invariants, JSON Pointer as the location primitive, position maps for line:column. No blank nodes — RDFC-1.0 shows what that avoidance buys.

## 1. RFC 8785 JCS versus "sorted keys + compact + integers only"

**The rules** (https://www.rfc-editor.org/rfc/rfc8785.html). Input must be I-JSON (https://www.rfc-editor.org/rfc/rfc7493): no duplicate names, strings expressible as Unicode, numbers expressible as IEEE-754 doubles (§3.1). No inter-token whitespace (§3.2.1). Strings: only `"`, `\` and U+0000–U+001F are escaped; `\b \t \n \f \r` use short forms, other controls use **lowercase** `\u00hh`; everything else, including non-ASCII, is literal UTF-8; lone surrogates MUST abort (§3.2.2.2). Numbers: serialized per ECMA-262 `Number::toString` including "Note 2"; NaN/Infinity MUST abort; `-0` becomes `0` (§3.2.2.3, Appendix B). Appendix B pins the behaviour: `0x4340000000000000 → 9007199254740992`, `1e21 → 1e+21`, `1e-6 → 0.000001`, `1.0 → 1`; the thresholds are ECMAScript's — scientific notation at magnitude ≥ 1e21 or < 1e-6, exponent sign always explicit (https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/toString). Property names are sorted recursively by **UTF-16 code units** compared as unsigned integers; array order is never changed (§3.2.3) — the RFC's own example places `"😀"` (U+1F600) before `"דּ"` (U+FB33), the signature of UTF-16 order.

**Implementations.** JS: `canonicalize` 4.0.0 (npm, 2026-08-12; https://github.com/erdtman/canonicalize) is `JSON.stringify` plus `Array.prototype.sort`, which is why Node is conformant almost by construction. Python: `rfc8785` 0.1.4 (2024-09-27; https://github.com/trailofbits/rfc8785.py) sorts keys by `encode("utf-16be")`, rejects NaN/Inf and integers outside ±(2^53−1); Matrix's `canonicaljson` is *not* JCS. Elixir: `jcs` 0.2.0 (2025-03-31, 80k downloads; https://github.com/pzingg/jcs) documents a known miss (`1.0e23` for `1e+23`); `rfc8785` 1.0.0 (2026-07-24, 290 downloads; https://github.com/yaglo/rfc8785) matches `Number::toString`, sorts by UTF-16 and reports zero mismatches on the 100-million-value `es6testfile100m` corpus, but **requires OTP 29 / Elixir 1.20.2** — this machine runs OTP 28, so it is unusable in `graphonomous/` today.

**Measured divergences from JCS** (`json.dumps`, `JSON.stringify`, OTP `:json.encode`):

| value | JCS / Node | Python `json.dumps` | OTP 28 `:json` |
|---|---|---|---|
| `1.0` | `1` | `1.0` | `1.0` |
| `1e20` | `100000000000000000000` | `1e+20` | `1.0e20` |
| `1e-7` / `1e-6` | `1e-7` / `0.000001` | `1e-07` / `1e-06` | `1.0e-7` / `1.0e-6` |
| `-0.0` | `0` | `-0.0` | `-0.0` |
| `9007199254740993` | `9007199254740992` (parsed as double) | exact | exact |
| U+001F in a string | `\u001f` | `\u001f` | `\u001F` (uppercase) |
| U+007F in a string | literal | `\u007f` when `ensure_ascii=True` | literal |
| `NaN` | JCS: error; Node emits `null` silently | `NaN` (invalid JSON) | error |
| lone surrogate | JCS: error; Node emits `\ud800` | returned; UTF-8 encode raises | raises |
| key order `～`(U+FF5E) vs `😀`(U+1F600) | 😀 first (UTF-16) | ～ first (code point) | ～ first (byte order) |

Python's `sort_keys` sorts by code point and `ensure_ascii` defaults to `True` (https://docs.python.org/3/library/json.html); Elixir compares binaries bytewise, and BEAM maps above 32 keys iterate in hash order (measured `{"k32":32,"k23":23,…}`), so ordering must be explicit via `:json.encode_key_value_list/2` (https://www.erlang.org/doc/apps/stdlib/json.html); Jason has no ordering option (https://jason.hexdocs.pm/Jason.html).

**When the simple discipline is byte-identical to JCS** — exactly when all of these hold: (1) no non-integer numbers; (2) integers within ±(2^53−1), beyond which JCS itself is lossy; (3) code-point key order equals UTF-16 order — guaranteed for ASCII keys, violated only when one key holds a supplementary character and another a code point in U+E000–U+FFFF; (4) strings emitted as literal UTF-8 (`ensure_ascii=False`), with no C0 controls other than `\t` `\n` `\r` (which sidesteps the hex-case and DEL differences) and no lone surrogates; (5) `NaN`/`Infinity` rejected, never emitted. Matrix's Canonical JSON is prior art for exactly this restriction — integers only within `[-(2**53)+1, (2**53)-1]`, keys sorted by code point, non-ASCII as UTF-8 (https://spec.matrix.org/latest/appendices/#canonical-json) — and has interoperated across many implementations for a decade; its one deviation from JCS (code-point key order) is harmless under an ASCII-keys rule.

## 2. IPLD, CIDs, multihash

DAG-JSON's strict form sorts map keys by **UTF-8 bytes**, strips whitespace, encodes links as `{"/": "<cid>"}` and bytes as `{"/": {"bytes": "<base64>"}}`, forbids NaN/±Infinity, and says integer-valued floats "should be encoded **with** a decimal point" (https://ipld.io/specs/codecs/dag-json/spec/) — so DAG-JSON writes `1.0` where JCS writes `1`, and orders non-BMP keys differently. DAG-CBOR follows RFC 8949 §4.2 deterministic encoding (shortest ints, definite lengths, length-first key order, 64-bit floats, only tag 42; https://ipld.io/specs/codecs/dag-cbor/spec/, https://www.rfc-editor.org/rfc/rfc8949). The IPLD data model itself advises against floats in content-addressed data (https://ipld.io/docs/data-model/kinds/). A CIDv1 is `multibase(0x01 ‖ varint(codec) ‖ multihash)`; a multihash is `varint(code) ‖ varint(len) ‖ digest` (https://github.com/multiformats/cid). Relevant codes: `sha2-256=0x12`, `sha1=0x11`, `raw=0x55`, `dag-cbor=0x71`, `dag-json=0x0129`, `git-raw=0x78`, and a *draft* `json-jcs=0xb601`, "result of canonicalizing an input according to JCS" (https://raw.githubusercontent.com/multiformats/multicodec/master/table.csv).

**Fit.** IPLD buys algorithm agility and a link kind; it costs a *second* canonical form that contradicts JCS on key order and `1.0`, varint/multibase code in three languages (Node `multiformats` is mature; Elixir's `ex_multihash`/`ex-cid` are older community packages, https://github.com/multiformats/ex_multihash, https://github.com/nocursor/ex-cid), and a `{"/": …}` link syntax that leaks into every schema. At 10^4–10^5 records that does not pay. Native identity stays `sha256:<hex>` over JCS bytes; a CID is a *derived* identifier — `CIDv1(json-jcs, sha2-256)` wraps our exact digest with no re-hashing — emitted by an adapter, and git ids wrap the same way (`git-raw` + `sha1`/`sha2-256`).

## 3. in-toto Statements, SLSA Provenance, DSSE

**Shape.** A Statement is `{"_type":"https://in-toto.io/Statement/v1","subject":[RD…],"predicateType":<URI>,"predicate":{…}}`; subjects are "matched purely by digest" and assumed immutable (https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md). A ResourceDescriptor has `name, uri, digest, content, downloadLocation, mediaType, annotations`, at least one of `uri|digest|content`; `content` is for < 1 KB inlines, everything else is a pointer (https://github.com/in-toto/attestation/blob/main/spec/v1/resource_descriptor.md). The DigestSet vocabulary answers requirement (d) outright: `sha256`, `sha512`, `gitCommit`, `gitTree`, `gitBlob`, `gitTag` (40- or 64-hex over `<type> SP <size> NUL <content>`), `dirHash1`, all lowercase hex (https://github.com/in-toto/attestation/blob/main/spec/v1/digest_set.md). SLSA Provenance v1 separates `buildDefinition` (`buildType`, `externalParameters`, `resolvedDependencies[]`) from `runDetails` (`builder.id` = "the transitive closure of all entities that are trusted to faithfully run the build", `metadata`, `byproducts[]`) and fixes the git idiom `uri: git+https://…@refs/heads/main` + `digest: {gitCommit: …}` (https://slsa.dev/spec/v1.1/provenance). Closer to our receipts: **Test Result** (`result: PASSED|WARNED|FAILED`, `configuration[]`; https://github.com/in-toto/attestation/blob/main/spec/predicates/test-result.md), **Link v0.3** (`command[]`, `materials[]`, `byproducts` with `stdout`, `stderr`, `return-value` as an integer exit status; https://github.com/in-toto/attestation/blob/main/spec/predicates/link.md, https://github.com/in-toto/docs/blob/master/in-toto-spec.md), **SCAI** (attribute assertions with `evidence` descriptors; https://github.com/in-toto/attestation/blob/main/spec/predicates/scai.md), **Runtime Trace** (`monitoredProcess.hostID`; https://github.com/in-toto/attestation/blob/main/spec/predicates/runtime-trace.md) and SLSA's **VSA** — "policy P over inputs I yielded PASSED/FAILED" (https://slsa.dev/spec/v1.1/verification_summary).

**DSSE** signs `PAE(type, body) = "DSSEv1" SP LEN(type) SP type SP LEN(body) SP body` over the payload as opaque bytes, deliberately avoiding canonicalization so re-parsing can never differ from what was signed (https://github.com/secure-systems-lab/dsse/blob/master/protocol.md); bundles are order-independent JSON Lines of envelopes, `.intoto.jsonl` (https://github.com/in-toto/attestation/blob/main/spec/v1/bundle.md). The lesson transfers: **hash and store canonical bytes once; never re-canonicalize to verify.**

**Is our receipt a Statement?** Naturally: `subject = [outputs by digest]`, `predicate = {experiment: RD(gitCommit+path), runtime: RD(uri: oci://…@sha256:…), host, exitCode, inputs: [RD…], claim: <id>}` under a Graphonomous `predicateType`, borrowing Link's `return-value` and Test Result's `result` enum. **Over-engineering at G0:** DSSE signatures and key management, Sigstore identity, `builder.id` trust closure, SLSA levels/VSA, runtime traces. **Adopt the shape, not the envelope** — the payload bytes are already fixed, so DSSE/JSONL wrapping later costs nothing.

## 4. SCITT, transparency logs, Merkle inclusion

SCITT is now **RFC 9943** ("An Architecture for Trustworthy and Transparent Digital Supply Chains", June 2026, Proposed Standard; https://www.rfc-editor.org/rfc/rfc9943): Issuers sign Statements (COSE_Sign1 with CWT claims); a Transparency Service checks a Registration Policy — itself registered as a Signed Statement — appends to a verifiable data structure and returns a **Receipt**; Signed Statement + Receipt = Transparent Statement. Receipts are **RFC 9942** COSE Receipts (https://www.rfc-editor.org/rfc/rfc9942): a COSE_Sign1 carrying `vds` (label 395; `RFC9162_SHA256 = 1`) and `vdp` (label 396) with an inclusion proof `[tree size, leaf index, path[]]` or a consistency proof. The tree hash is RFC 9162's: `MTH({}) = HASH()`, `MTH({d0}) = HASH(0x00‖d0)`, `MTH(D[n]) = HASH(0x01‖MTH(D[0:k])‖MTH(D[k:n]))`, k the largest power of two < n; the 0x00/0x01 prefixes exist for second-preimage resistance (https://www.rfc-editor.org/rfc/rfc9162.html). Rekor v2 went GA on 2025-10-10 on a tile-based log (Tessera / C2SP tlog-tiles) with only `hashedrekord` and `dsse` entries, no signed entry timestamps, and clients expected to persist inclusion proofs beside artifacts (https://blog.sigstore.dev/rekor-v2-ga/, https://docs.sigstore.dev/logging/overview/). The C2SP checkpoint is small — origin line, decimal tree size, base64 root, signature lines (https://c2sp.org/tlog-checkpoint); tiles are 256-hash static files from which clients compute proofs themselves (https://c2sp.org/tlog-tiles).

**Verdict: wait, explicitly.** Every one of these protocols lets *third parties* detect equivocation by a *service*. G0 has one writer, one repo, and consumers who can clone the whole registry; a projection digest plus git history already answers "did this record exist in projection P?". Decide now only what makes later adoption free: leaf = `sha256(0x00 ‖ canonical bytes)` (RFC 9162 leaf form), manifests sorted so a tree can be built over them, and a projection-root record shaped like a checkpoint (`origin, size, root`). Revisit when there are multiple writers or a verifier who cannot trust the git remote — force-pushes make git append-only by convention only.

## 5. OpenLineage and W3C PROV for adapter runs

OpenLineage's RunEvent requires `eventTime, producer, schemaURL, run{runId: uuid}, job{namespace, name}`; `eventType ∈ {START, RUNNING, COMPLETE, ABORT, FAIL, OTHER}`; every facet carries `_producer` and `_schemaURL` (an immutable, tag-pinned URL); events for one run are cumulative (https://openlineage.io/spec/2-0-2/OpenLineage.json, https://openlineage.io/docs/spec/run-cycle, https://openlineage.io/docs/spec/facets/). We would map to `sourceCodeLocation` (`type, url, repoUrl, path, version=commit, tag, branch`; https://openlineage.io/docs/spec/facets/job-facets/source-code-location) and the dataset `version` facet (`datasetVersion`; https://openlineage.io/spec/facets/1-0-1/DatasetVersionDatasetFacet.json). PROV supplies the vocabulary: Entity / Activity / Agent, `used`, `wasGeneratedBy`, `wasDerivedFrom`, `wasAssociatedWith` (with a `prov:Plan`), `wasAttributedTo`, `prov:SoftwareAgent`, `prov:Bundle` ("a named set of provenance descriptions, and is itself an Entity"), `startedAtTime/endedAtTime` (https://www.w3.org/TR/prov-dm/, https://www.w3.org/TR/prov-o/); PROV-JSON is a 2013 Member Submission with typed values as `{"$": v, "type": t}` (https://www.w3.org/submissions/prov-json/).

**What an adapter run record must carry** for a replayable projection, split into an identity part (hashed) and a witness part (not hashed):

- identity: `adapter` = RD with `gitCommit` (+ path) and, when containerized, the image `sha256`; `inputs[]` = RDs with `gitBlob`/`sha256` digests and source path (the blob digest, never a working-tree path alone); `params` (canonical object); `outputs[]` = record hashes produced; `sourceCommit` of the registry snapshot.
- witness: `startedAt/finishedAt` (RFC 3339, I-JSON §4.3), `host` URI, `exitCode`, log digests, `runId` (UUIDv7, as OpenLineage recommends).

The replay rule then becomes checkable: **same adapter digest + same input digests + same params ⇒ same output digests**; a violation is a nondeterminism finding, not a new fact. Export: identity part → PROV (`Activity` with `used`/`wasGeneratedBy`/`wasAssociatedWith` + `Plan`) or an OpenLineage COMPLETE event with `sourceCodeLocation`; both are adapters.

## 6. Order-independent digests: sets, git trees, RDFC-1.0

**Hash of sorted hashes** is the deployed baseline: Go's module `dirHash1` is `sha256` over lines `"<hex>  <name>\n"` sorted by name — literally `sha256sum $(find . -type f | sort) | sha256sum` (https://pkg.go.dev/golang.org/x/mod/sumdb/dirhash) — and in-toto adopted it as a DigestSet algorithm. It is order-independent because the sort key (the logical id) is unique, and unambiguous because entries are fixed-width or delimited. A **sorted-leaf Merkle tree** (RFC 9162 MTH over leaves ordered by id) costs one more function and buys O(log n) inclusion proofs and consistency proofs between projections — worth publishing as a *second* root derived from the same manifest, not as the definition.

**Git trees.** An object is `"<type> <size>\0" ‖ content` hashed; a tree is a sequence of `<mode> SP <name> NUL <binary digest>` entries (https://git-scm.com/book/en/v2/Git-Internals-Git-Objects). Measured in a fresh `git init --object-format=sha256` repo: the raw tree stores the directory mode as `40000` (ls-tree prints `040000`); files `a.txt`, `a0` and directory `a` come out `a.txt, a, a0` — not byte order `a, a.txt, a0` — because git compares a directory as if its name ended in `/` (`base_name_compare` in `tree.c`: `if (!c1 && S_ISDIR(mode1)) c1 = '/'`; https://raw.githubusercontent.com/git/git/master/tree.c); `git mktree` normalizes order for callers (https://git-scm.com/docs/git-mktree); blob ids equal `sha256("blob 1\0x")` exactly as in the SHA-1 formula, and SHA-1 and SHA-256 names of one object are unrelated (https://git-scm.com/docs/hash-function-transition). So a git tree of canonical files *is* a valid content-addressed set digest and a convenient witness — `git write-tree` over a directory of canonical files reproduces it — but as the *definition* it imports mode bits, a type-dependent name order, the SHA-1 default, and the `write-tree`-returns-the-empty-tree trap already in this repo's memory. Define the projection digest in our own terms; publish the git tree id beside it as a cross-check.

**RDFC-1.0** exists because RDF has blank nodes: canonical labels come from hashing first-degree and then N-degree neighbourhoods, and adversarial "poison" graphs force worst-case behaviour, so implementations MUST bound N-degree calls and abort (https://www.w3.org/TR/rdf-canon/). Its output — canonical N-Quads sorted by code point and hashed with SHA-256 — is what a graph digest looks like once every node has a name. If every G0 node carries a stable logical id and edges are records keyed by `(src, predicate, dst)`, there are no blank nodes and canonicalization degenerates to "canonical records, sorted by id, hashed" — the manifest above. Verifiable Credentials ships both routes side by side (`eddsa-rdfc-2022` and `eddsa-jcs-2022`, W3C Recommendation 2025-05-15; https://www.w3.org/TR/vc-di-eddsa/); we take the JCS route and forbid anonymous nodes by schema.

## 7. Validation and diagnostics with exact locations

JSON Schema 2020-12 defines output units of `valid`, `keywordLocation` (pointer into the schema), `absoluteKeywordLocation`, `instanceLocation` (an RFC 6901 pointer into the instance) and `error`/`annotations` — and says nothing about line or column (https://json-schema.org/draft/2020-12/json-schema-core). Two traps: `format` is an *annotation* by default (assertion "MUST be disabled by default"; https://json-schema.org/draft/2020-12/json-schema-validation), so a `sha256:` digest must be constrained with `pattern`; and `$dynamicRef`/`unevaluatedProperties` need a real 2020-12 engine. Engines: Ajv's `Ajv2020` (errors carry `instancePath` as a JSON Pointer plus `schemaPath`, `keyword`, `params`; https://ajv.js.org/json-schema.html); python-jsonschema's `Draft202012Validator` (`absolute_path`, `json_path`, `schema_path`; https://python-jsonschema.readthedocs.io/en/stable/errors/); Elixir's JSV, claiming full 2020-12 including `$dynamicRef` (https://github.com/lud/jsv) — `ex_json_schema` stops at draft-07. SHACL validates RDF graphs and returns `sh:ValidationResult` with `sh:focusNode`, `sh:resultPath`, `sh:value`, `sh:sourceShape`, `sh:resultSeverity` — semantically rich, positionally blind, and only meaningful once records are RDF (https://www.w3.org/TR/shacl/). Neither schema language expresses what makes a ledger a ledger — status transitions, "every REFUTED claim cites a receipt", cross-file referential integrity — so a custom validator is needed regardless; JSON Schema's job is to reject malformed *shape* early with a pointer.

**Getting to line:column.** JSON Pointer (`/`-separated tokens, `~0`/`~1` escapes, `~1` decoded first; https://www.rfc-editor.org/rfc/rfc6901) is the location primitive; RFC 6902 patches (`add/remove/replace/move/copy/test`, atomic) are the natural encoding of promotions and corrections (https://www.rfc-editor.org/rfc/rfc6902). Parsers report positions only for *syntax* errors — Python's `JSONDecodeError` has `lineno/colno/pos`, Jason's `DecodeError` a byte `position` — so semantic diagnostics need a **position map**: JS `json-source-map` yields, per pointer, `key/keyEnd/value/valueEnd` with `{line, column, pos}` (https://github.com/epoberezkin/json-source-map); Python `json-source-map` 1.0.5 yields `Entry(value_start, value_end, key_start, key_end)` with zero-indexed `line/column/position` (declared for 3.8–3.11; https://pypi.org/project/json-source-map/). For Markdown: mdast/remark nodes carry unist `position.start/end` with 1-indexed `line`/`column` and 0-indexed `offset` (https://github.com/syntax-tree/unist); markdown-it-py block tokens carry `map = [line_begin, line_end]`, inline children `None` (https://markdown-it-py.readthedocs.io/en/latest/api/markdown_it.token.html); Earmark's AST quadruple `{tag, attrs, children, meta}` carries `%{line: n}` only on some node kinds, while warnings are `{severity, line, message}` (https://earmark-parser.hexdocs.pm/EarmarkParser.html; vendored `earmark_parser` 1.4.44 under `graphonomous/deps` confirms). Recommendation: one diagnostic shape — `{source: RD(gitBlob), pointer, range: {start: {line, column, offset}, end}, code, message}` — with the position map computed in whichever runtime parsed the source; Elixir consumes Node/Python maps rather than growing a JSON position parser at G0.

## Proposed canonicalization rule set (G0 profile of RFC 8785)

Rules 1–10 restrict the value domain; under them, rules 11–15 produce bytes identical to RFC 8785 output, so any conformant JCS library is a valid implementation and the hand-rolled encoders in Python, Node and Elixir are too.

1. **Value domain.** A record is a JSON object whose values are objects, arrays, strings, integers, `true`, `false`, `null`. No other JSON number may appear in an identity-bearing record.
2. **Integers** satisfy −(2^53−1) ≤ n ≤ 2^53−1; anything larger is a string (I-JSON §2.2). Validators reject, never round.
3. **Non-integer quantities** are strings in a declared field type (`"0.30"`, scale in the schema); `-0`, `NaN`, `Infinity` cannot occur.
4. **Keys** are ASCII, match `^[A-Za-z_][A-Za-z0-9_]*$`, and are unique per object — this makes code-point, byte and UTF-16 orders coincide.
5. **Strings** are well-formed Unicode scalar values (no lone surrogates or noncharacters, RFC 7493 §2.1) with no C0 control other than U+0009, U+000A, U+000D and no U+007F. Newlines are LF; encoders never normalize text — validators reject CR LF at the boundary.
6. **Arrays** are ordered; a set-valued field is declared in the schema and sorted by the canonical bytes of its elements before hashing; duplicates are rejected.
7. **Absent vs null.** Optional fields are omitted, never `null`; `null` appears only where a schema types it. Encoders never emit keys for absent values.
8. **Identity vs witness fields.** Every record type declares its identity-bearing fields; the hash is computed with witness fields removed. Timestamps, hostnames, durations and log excerpts are witness fields unless a schema says otherwise.
9. **Logical id ≠ hash.** `id` is a stable schema-defined string (e.g. `claim:INV-R9.4`); the hash is never stored inside the hashed bytes.
10. **References** to records are the target's `id` plus, where version-pinned, its `sha256:` hash; references to external artifacts are ResourceDescriptors (rule 16).
11. **Serialization**: UTF-8; no whitespace between tokens; object members sorted by key using unsigned code-unit comparison (byte order, by rule 4); arrays in stored order.
12. **String escaping**: `"` → `\"`, `\` → `\\`, U+0009/U+000A/U+000D → `\t`/`\n`/`\r`; every other character literal. (Python: `ensure_ascii=False`; OTP `:json` and Node: defaults.)
13. **Integers** print as optional `-` then decimal digits without leading zeros; literals are `true`, `false`, `null`.
14. **Hash** = SHA-256 over the canonical bytes; string form `sha256:` + 64 lowercase hex. `sha256` is the only algorithm at G0; the prefix exists so a second can be added without re-hashing.
15. **Leaf and root**: leaf = `SHA-256(0x00 ‖ canonical bytes)`; a projection manifest is a record `{kind:"projection", entries:[[id, hash]…] sorted by id, count}`; the projection digest is that record's hash; an RFC 9162 root over the same sorted leaves may be published beside it.
16. **External artifacts** are ResourceDescriptors restricted to `{name?, uri, digest:{alg:hex}, mediaType?}`, `alg ∈ {sha256, gitCommit, gitTree, gitBlob, dirHash1}`; `content` is never embedded; a `gitCommit` from a SHA-256 repo is 64 hex and the `uri` must say so.
17. **Conformance gate**: CI hashes the RFC 8785 Appendix B integer rows, the §3.2.3 sorting example restricted to ASCII keys, and a fixed corpus of G0 records in Python, Node and Elixir, failing on any single-byte disagreement between runtimes — the `1.0` incident is why this gate exists, and it is never satisfied by a runtime agreeing with itself.
18. **Widening path**: lifting rule 4 (non-ASCII keys) or rule 1 (floats) is a profile change that switches all three runtimes to full RFC 8785 libraries at once (`canonicalize`, PyPI `rfc8785`, hex `rfc8785` once OTP 29 is in use); until then the restrictions stand.
